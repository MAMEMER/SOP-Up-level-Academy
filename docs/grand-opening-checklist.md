# Grand Opening checklist

`/grand-opening-checklist` uses the existing SOP Google staff allow-list/session and navigation. Any staff role can write; view-as sessions are read-only. Local development without credentials uses clearly labeled, user-scoped local preview; it cannot write shared data.

Storage: server-only `sop_grand_opening_checklist/{id}`, with immutable `history/{uuid}` subcollection. Fields: title, category, day (`17`, `18`, `ทั้งสองวัน`, or empty), nullable nonnegative finite quantities (max 1,000,000), assignee, note; revision, done/doneBy/doneAt, createdBy/createdAt, updatedBy/updatedAt, deleted. API rejects client audit fields. Actor names and timestamps come from the server session/clock. Each mutation and before/after history commit atomically with revision conflict detection. Deletion is a tombstone, preserving history and preventing seeds from reappearing. History returns the newest 100 events.

Like Influencer Tracker, 37 stable virtual seeds are overlaid with saved rows. GET never seeds or bulk-writes production. First mutation materializes the row; a seed's creator is “รายการเริ่มต้น”. Seeds remain editable. No recurring checklist windows, daily store task/KPI records or planned-day scheduling are changed: those infrastructure modules are designed for recurring work, not this shared event inventory.

GET `/api/grand-opening-checklist`: snapshot, or `?id=` history, or `?stream=1` authenticated SSE backed by an Admin Firestore snapshot listener. Each connection closes after 50 seconds; EventSource reconnects automatically. Abort/cancel/error removes the listener. No public client Firestore access/rules changes. POST actions: save (fields), tick (done), delete; all require id and expected revision. No database writes are performed for development screenshots or verification.

Progress reflects saved active rows, unaffected by filters. Day 17/18 includes both-day rows; untagged rows only appear in all-days. Drafts survive reload in user-scoped localStorage; Reset explicitly discards a draft. Save conflicts retain drafts and reload shared state. Ticking is disabled while a row has an unsaved draft to avoid changing its revision mid-edit. Export includes drafts and history already opened, not a complete audit backup.

Preview screenshots are stored under `docs/screenshots/`. Merge and production deploy require Champ's approval.

## Compact checklist and photos

Categories start collapsed and show saved done/total counts. Rows show a checkbox, truncated title, optional have/need quantities, ticker and photo count. Tap a row for notes, edit form, photos and audit history. Completed rows are hidden by default; “แสดงที่เสร็จแล้ว” reveals them. Selecting status “เสร็จ” also reveals completed rows; turning the toggle off clears that status. Filters, category/panel expansion and existing drafts survive reload in the same user-scoped localStorage. Add opens the relevant category and edit panel. Progress continues to count all saved active items.

Photos reuse the existing Firebase Admin Storage bucket and staff session authorization. POST multipart (`id`, `revision`, `file`, `thumbnail`) adds one photo at a time; JSON `image-delete` with `imageId` removes its active reference. Maximum 12 photos per item; JPEG/PNG/WebP/GIF, 4MiB after client compression, 30MiB original client limit. The existing downscale helper handles large camera photos (1600px/JPEG); thumbnailFor creates a separate 220px JPEG. Unsupported HEIC needs conversion to JPEG. SVG/PDF and empty files are rejected. Unsaved drafts must be saved/reset before attachments; local preview disables shared uploads.

`images[]` stores only id, Storage paths, filename, MIME type, size, uploader name and timestamp. Files live under `sop-grand-opening/{itemId}/{imageId}` with a separate `-thumb` object. No image bytes or public download tokens are stored in Firestore. Authenticated GET `?id=...&image=...` serves an active attachment; `&thumb=1` serves its thumbnail. The browser loads thumbnails first and the full photo only in a native dialog (Escape, focus trap and focus restoration). Add/delete is revision checked and commits its before/after audit atomically. Failed/conflicting uploads clean up newly uploaded objects. Removing a photo retains its Storage object for audit recovery, while normal reads refuse deleted attachments/items. No schema migration, production writes, or rules changes are required.

Verification uses mocked staff/Storage API tests and local browser fixtures, never production data. The `go-compact-*` screenshots show seeded data and a real existing training photo substituted for the mock image response. Browser checks include a 10.9MB camera image compressed to 370KB, add/delete history, hidden/revealed completed rows, responsive layout and lightbox keyboard behavior. Live Storage permissions and cross-device realtime should be smoke-tested after an approved deployment.
